# guide/

**Forward-looking planning and todos.**

Answers the question: *what are we building next, and how?*
Segment-by-segment workplans, cross-cutting checklists, and
ad-hoc todo lists live here. Once a segment ships and its plan
becomes a historical record, move it into `guide/archive/` —
and add a row for it to `guide/archive/README.md` in the same
change (that index is maintained by hand). The same applies to a
**settled assessment or audit**: once its question is answered and
the answer lives somewhere durable, it archives like a plan.

**Both indexes are checked.** `tests/unit/test_guide_indexes.py`
fails if a document here matches no row and no documented shape, or
if an archived document has no row at all — the rule below was prose
only until 2026-09-12, and both folders had drifted under it. It also
rejects a shape row broad enough to cover files nobody indexed, since
that failure is silent and green where a broken parse is loud.

**Before archiving a plan, run `python3 tools/close_check.py <id>`**
(`19A` for a segment, `19A.3` for one item) **and get exit 0.** It
verifies that the spec edits the plan committed to in its `Doc impact`
section actually happened — the "spec on the way out" half of the phase
rule, which nothing checked before 2026-09-05. It reports; you act. It
cannot tell you whether an edit was *right*, so run `spec-writer` over
the same files afterwards.

**Every 8 weeks, or 500 merges since the last sweep — whichever comes
first — run a drift sweep.** `python3 tools/close_check.py --stale`
answers whether one is due and orders the reading; copy
`sweep_template.md` to `guide/sweep_<YYYY-MM-DD>_<scope>.md` (the dated
filename is what `--stale` reads to find the previous sweep). The sweep
is the close check's complement, not its repeat: a close check reads only
the paths one plan committed to, so a spec no segment ever named is
invisible to it — on 2026-09-05, 13 of 64 live docs had not been touched
since the previous sweep. Two triggers because either alone misleads; the
gap that motivated this was 93 days *and* 1,120 merges.

| Path | Covers |
|---|---|
| `segment_*.md` | Plans for the current and upcoming segments. |
| `sweep_template.md` | Blank drift sweep — carried-forward findings first (the 2026-05-11 sweep's two Tier-1 gaps sat 117 days because the next sweep never re-read them), then findings by disposition (write/deepen · update · consolidate · retire · move), then every file read with no finding, then every in-scope file *not* read. Ends with the five entry-point commands — staleness, dropped commitments, orphan specs, dead cross-references, the app diff since the last sweep. A sweep recommends; the fixes ship afterwards as ordinary work. It carries no `Doc impact` and `close_check.py` does not read it. Planned in `segment_19A_spec_documentation.md` Item 2. |
| `findings_<YYYY-MM-DD>_<scope>.md` | An open register of discrepancies a sweep or audit surfaced but did **not** act on. Distinct from a sweep record, which says what was *changed*: a findings file says what was *found and left standing*, because `rrw_sdd_in_practice.md` §4 makes `spec/` the contract — a sweeper who finds spec and code disagreeing may not quietly rewrite the spec to match, so the divergence becomes a finding rather than an edit. Rows are tagged by kind (spec-vs-code, spec-vs-spec, spec-internal, code-internal, stale identifier) and each names what deciding it involves, since most are a choice between *fix the code* and *change the contract deliberately* — the author's call, not a sweep's. Retire the file when its rows are actioned or moved into a segment plan; archive it, do not delete it, since the reasoning is the value. |
| `sweep_<YYYY-MM-DD>_<scope>.md` | A dated sweep's working notes. The filename's date is machine-read by `tools/close_check.py --stale`; keep the shape. **Every dated sweep must declare `<!-- sweep-scope: corpus -->` or `<!-- sweep-scope: partial -->`** — only a *corpus* sweep (the whole `spec/` + `docs/` + root corpus) resets the 8-weeks / 500-merges cadence; a *partial* one is recorded and listed but moves nothing. The scope cannot be read off the filename, whose `<scope>` slug is free text, and an unmarked sweep raises rather than being guessed at (2026-09-12: before this, the single-file 2026-09-10 sweep reset the clock from 230 merges / 7 days to 61 / 2). **The newest *corpus* sweep stays here until a newer corpus sweep supersedes it** — `last_sweep_date()` globs `guide/` non-recursively, so archiving it does not error, it silently turns the staleness trigger off: `--stale` goes from "not due, 3 d of 56, 100 of 500 merges" to "No dated sweep found" and exits 0 either way. Archive older sweeps, and superseded partial ones, freely (2026-09-08; corpus rule 2026-09-12). |
| `segment_plan_template.md` | Blank segment / item plan with every section prompted — Opportunity → Decision → Semantics → Judgment calls → Blast radius (measured) → PR ladder → Definition of done → Open questions → Out of scope → Doc impact (+ a Status block added when intended and done diverge). Two headings are machine-read by `tools/close_check.py` (`## Doc impact`, `## Status`); do not rename them. `Doc impact` is matched exactly, so suffixing it retires a manifest without deleting it; `Status` tolerates a suffix. The operational guide for using it is the `segment-plan` skill (`.claude/skills/segment-plan/SKILL.md`). |
| `codebase_assessment_*.md` | Codebase-vs-functional-spec snapshots — **the Claude Code lineage**. Only the latest snapshot *of this lineage* lives here; older ones retire to `archive/` once a newer **`codebase_assessment_`** supersedes them. A `codex_assessment_` never supersedes one of these (2026-09-12). **Sidecars:** only the latest snapshot's `codebase_assessment_<date>.json` is kept — it is the next snapshot's delta baseline and nothing else reads one — and older sidecars are deleted rather than archived, since any of them comes back from history — `git show df4ecae3:<path>` for the eight retired on 2026-09-30, and in general from the commit that added it (`git log --diff-filter=A -- <path>`), not the snapshot's pinned SHA, which predates its own sidecar (2026-09-30). `guide/assessment.json` excludes them from the `docs` area. **Standard quantitative items:** LOC + biggest files (as before), plus duplication and churn from `python3 tools/code_metrics.py` — added 2026-09-04 after `docs/archive/practice-audit-2026-09-04.md` Appendix A found both unmeasured. Quote the churn figure with its baseline ratio, never alone. **Record them every time; act on them only past a threshold** — duplication at >=10-line blocks rising materially between assessments (the 2026-09-04 baseline is 6.5% for `app/`), or a churn ratio meaningfully above ~1.5x (baseline 1.0x, i.e. deletions are age-blind). The churn figure is deterministic — the tool walks the full merge history, ~76s; `--churn-sample` output is sample-dependent at any size and is not comparable between snapshots. Below those, the numbers are a trend line, not a task: 6.5% duplication is fine, and "improving" it is how a recurring metric turns into make-work. These are reading prompts for a human in a document that is already judgement-based — deliberately not a CI gate, which is the form that gets argued with, raised, then disabled. |
| `codex_assessment_*.md` | Whole-repository assessments — **the Codex lineage**, opened 2026-09-12. Same retention rule within itself: the newest stays, older ones archive. Kept as a **separate lineage** rather than folded into the series above, because the two answer the same question independently and a reader comparing them wants both reads, not the later one only — so neither supersedes the other and both can be live at once. Differences worth knowing: a Codex assessment is a fresh-context read rather than a delta narrative, and carries **no `.json` sidecar**, so it is never the delta baseline for a `codebase_assessment_`. Both lineages are dated records, and both are exempt from the live-prose path check via `DATED_DOC` in `tests/unit/test_doc_references.py`. |
| `post_azure_todo_checklist.md` | Work **blocked on the institutional Azure deployment concluding** (the host serves Review Robin since 2026-10-31; items 1 and 2 can be worked now) — not merely unscheduled, which is `todo_master.md` / `deferred_consolidated.md`. Deliberately separate from the NUS deployment runbook (kept privately with the deployment): that runbook will be rewritten repeatedly as details settle with IT, and an item parked in a section about to be rewritten is an item about to be lost. Each entry names what to do, where, and how to tell it is done. Items leave when done, or when the runbook stops moving and can hold them. Opened 2026-09-08 (19G Item 10). |

No email is delivered and nothing runs on a clock; the note sets out the delegated-versus-shared-mailbox disagreement, recommends two send paths and an in-app clock, and lists the author's three choices. It feeds segment 14B and leaves when that plan absorbs it. |

All-or-nothing as replace is; a row already on the roster, or on an account already there, is refused. An upsert tick (update matched rows, add the rest, blank cells keep) and a Validate warning for two rows on one directory account follow (amendment, 2026-10-31). |

| `archive/` | Shipped segment plans (kept for historical reference, and the record of what shipped; not the source of truth for current behavior — that is `spec/`). The early `low_intensity_workplan_review_robin_web.md`, `major_refactor.md`, and `rules_table.md` are archived here too — superseded by the segment plans + `todo_master.md` and (for `rules_table.md`) the seed table in `spec/assignments.md` (which absorbed the pre-2026-05-26 `rule_based_assignment.md`, now under `spec/archive/`). `archive/README.md` is a hand-maintained index of every file in the folder — keep it in sync when you archive something. |

Sibling folders:

- **`spec/`** — surface specifications and design intent (what
  the UI should look like).
- **`docs/`** — reference material about the running system (how
  things actually work today).
